## Integration contracts

D1. Issues view adds an injectable `loadIssuePage({bucketId, cursor, limit})` seam. Result: `{ok, issues, total, hasNextPage, error?}`; each issue carries its server `cursor`. Request limit is an upper bound derived from body-row budget, NOT fixed20. Complete-title wrapping decides how many fetched rows fit; the next page starts after the last SHOWN row's cursor, not after unused fetched rows. Keep cursors per bucket/page. Previous/next/refresh fetch fresh. Resizing resets page boundaries safely; stale async results must not overwrite newer navigation. Existing static pages mode remains testable without network.

D2. GitHub client adds `getIssuePage({query, after, first}, opts)`, `listAssignableUsers(opts)`, and `editAssignees(number, {add, remove}, opts)` with fixed argv and explicit failure results. Issue detail carries explicit `permissions: {canEditLabels, canEditAssignees, canCreateLabels}` booleans derived from authoritative GitHub capabilities/role semantics (unknown=false). The view defaults edit permissions to false until established; hide both footer hint and editor entry when false. Existing labels/assignees are preselected and saved as add/remove deltas. GitHub remains final authority. A page returns edges' cursors on normalized issues. Preserve existing public helpers unless this task explicitly supersedes behavior. Assignee editor saves through `actions.editAssignees`; view gets `loadAssignees`. Successful comments/labels/assignees invalidate and refetch the selected detail through `loadIssue(number, {refresh:true})`.

D3. Issues/ODD/worktree-detail use Tab only for datasets/tabs; left/right only paginate the active list. Delete clears the entire input only in active search/name inputs where requested; Backspace remains character deletion. All hints stay on a single footer row. ODD names and issue titles use viewport-aware row budgeting, not a fixed document count.

D4. Reuse this thread worktree. Independent view, GitHub-client, and warp/create units run with disjoint edit surfaces. Extension orchestration happens after their contracts are delivered, not in an oversized concurrent integrator. Tests/docs ship with each behavior; full-suite and real TUI checks follow stable integration. No publishing.
