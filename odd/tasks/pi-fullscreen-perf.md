## Specs

S1. Goal, verbatim: "Reducir CPU por frame, RAM retenida y costo de scroll/redraw en `tuiMode: \"fullscreen\"` para sesiones largas, mediante optimizaciones **dinámicas** (basadas en visibilidad, recencia o dirty-tracking), no sólo knobs estáticos. El colapso dinámico del output de tools es *una* idea entre varias: evaluá alternativas y elegí con evidencia medida."

La implementación de la que resulte mejor, en un worktree, con tests donde aplique y sin commitear. 4. Lo que empeoró, si algo empeoró, dicho explícito. 5. Si el resultado es un setting dinámico: semántica propuesta (default, cómo se apaga, cómo interactúa con Ctrl+O) y por qué ese default."
S3. S7. Baseline numbers already measured on pi-tui 1.3.0 (terminal 100x40, synthetic markdown+tools): steady-state fullscreen frame 0.35/0.95/1.39 ms at 200/1000/2000 messages; frame after scrolling 0.10/0.42/0.80; regular-mode diff 0.21/0.70/1.35; COLD REBUILD 8.7/40.9/72.6 ms; retained heap ~13-25 KB per message. Realistic rows: 500 turns 23,500 lines 1.55 ms/frame 13.7 MB all-expanded vs 3,900 lines 0.39 ms 10.9 MB with the last 10 expanded; 2000 turns 94,000 lines 4.87 ms 35.9 MB vs 14,400 lines 0.78 ms 24.3 MB. Read: the steady frame is NOT the main cost; retained memory, cold rebuild and per-scroll-event cost are.
S8. The render model already verified, NOT to be re-researched: transcript is not virtualized; `renderLayoutFrame()` builds a NEW `renderCache` per frame (`packages/tui/src/layout.ts:~389`); `renderCached()` (~69) is intra-frame only; the `scroll` node (~135) materializes EVERY line of the document into `box.scrollContentLines` (162) and `paintBox` clips only at paint time; `ScrollView.render()` (`components/scroll-view.ts:~215`) does not clip vertically; `Container.render()` (`tui.ts:~405`) always walks every child; `createChatViewport()` wraps the whole `documentContainer` in one ScrollView and nobody prunes old components; in fullscreen `TuiAltScreen.doRender()` (~1679) writes only the viewport rows, so the full replay problem belongs to `regular` mode. O(N)-per-frame, in weight order: (1) full-document `renderCached` + `scrollContentLines`; (2) Container/layout walk; (3) with Ctrl+F open, `refreshSearch()` (~595) scans all lines each frame and `buildSearchCorpus()` (`alt-screen-search.ts:~162`) rebuilds the whole corpus while streaming.
S9. Hypotheses to test, ordered by expected value, each one to be CONFIRMED or KILLED with a number: H1 cached per-child heights between frames (index keyed by width + content generation, only invalidated children recomputed, `contentHeight` derived from the index; `scrollContentLines` semantics preserved or derived, because search and selection read it). H2 bounded LRU eviction of rendered lines outside the viewport (`invalidate()` on exit, re-render on return), content-preserving. H3 dynamic recency collapse from `packages/coding-agent` via `pi.registerToolRenderer`, wrapping `renderResult`; on collapsing call `inner.invalidate()` and drop the inner component; an app-supplied `expanded: true` (Ctrl+O) is a sticky user override that wins; gate on `ctx.mode === "tui"` because the same renderers draw exported HTML; count by TURN (user messages), never by tool call, because one turn can fire 15 parallel tools; per-row expansion must stay available. H4 the cost of open Ctrl+F while streaming. H5 possible `WeakRef` token thrash (GC between frames forcing a markdown re-parse of a visible message). H6 `bash-execution`/`visual-truncate` preview re-cutting and re-wrapping the same long output every frame; cache by (output length, width). H7 Kitty images (`prepareKittyScreen`/`imageAnchorsNeedRedraw`) forcing full-screen frames.
S10. Honesty rules for this feature: a synthetic benchmark is labelled synthetic; a discarded hypothesis is named with the number that discards it; anything that got WORSE is said explicitly; and "the steady frame is fine" is not a licence to skip measuring.

S13. Question raised by the user before shipping H3: pi ALREADY has a manual collapse — `app.tools.expand` (`ctrl+o`, `packages/coding-agent/docs/keybindings.md:164`) flipping `setToolsExpanded(collapsedOrExpanded)` globally over every tool. So is H3 just "collapse more", or does it do something the existing mode does not? The structural difference is that H3 additionally calls `inner.invalidate()` and DROPS the inner component, while `ToolExecutionComponent.updateDisplay()` (`components/tool-execution.ts:270`) hands the PREVIOUS component back to the renderer through `getRenderContext(this.resultRendererComponent)`, so a collapsed-but-reused component may stay referenced: the drawing changes and the memory may not. That was never measured — only H3 against the normal state. Fixed: measure three variants at 5000 turns on the same harness — (1) everything expanded (already known: 107.7 MB), (2) everything collapsed the way `ctrl+o` collapses it, through the REAL `ToolExecutionComponent` if it can be driven, (3) H3 (already known: 81.3 MB). If (2) lands near (3), H3 buys automation, not memory, and that must be said. If (2) lands near (1), the manual collapse is cosmetic and the better fix is making the MANUAL collapse free its component — same behaviour as today, none of H3's surprises. The answer decides whether the panel's row is "recency collapse" or whether the work moves to "make the manual collapse release".

S14. Decision, taken after the user asked whether H3 is "an optimization of the EXPANDED mode" and the code confirmed the framing was wrong. It IS, and only that: `interactive-mode.ts:513` declares `private toolOutputExpanded = false`, i.e. pi's DEFAULT is COLLAPSED, and with the policy enabled `rowIsExpanded` (`tool-output-collapse.ts:143`) falls through to `rowIsWithinRecencyWindow(...)`, so turning H3 on EXPANDS the last 10 turns — in the default state it ADDS work instead of removing it. Its −53% frame and −25% heap were measured against everything-expanded (the collapse benchmark's variant A), a state a user reaches only by pressing Ctrl+O and leaving 200 turns open. Therefore H3 is DROPPED as a product optimization, and the work moves to the design the user proposed and Gemini CLI ships (PR #19010): Ctrl+O toggles expansion of the CURRENT TURN only, older turns stay collapsed, and a new prompt re-constrains — that auto-reset already exists here (`interactive-mode.ts:3550-3557`). That leaves pi's default untouched, makes expanding cheap, and removes a whole piece: no recency policy, no 10-turn threshold, no switch for it. The `collapseOldToolOutput` setting is to be REPLACED by one whose name and description state what it does — bound Ctrl+O to the current turn. Whether the collapse must ALSO free the inner component is exactly what T13 measures.

S16. T13 verdict, measured through the SAME real apparatus (real `ToolExecutionComponent` + real bash renderer) at 5000 turns: expanded 199.1 MB gc'd, MANUAL collapse 178.7 MB (−10.3%), automatic keep=10 collapse 127.5 MB (−36.0%) — the manual saving is 28% of the automatic one, so the existing `ctrl+o` collapse is mostly cosmetic. Cause, in code: `updateDisplay()` (`components/tool-execution.ts:270`) hands the previous component BACK at `:318-320` instead of invalidating and dropping it, and the rebuilt preview keeps the full styled output string (`renderers/bash.ts:50-68`; `visual-truncate.ts` holds `options.text`), so a complete copy of every output stays referenced per row. The automatic path wins by dropping the whole inner component (`tool-output-collapse.ts:220-221`) and keeping only the raw result the app already holds. Consequences, both required by this design: (a) a collapse — manual or automatic — must actually FREE, so the manual path gets `invalidate()`-plus-drop on the expanded→collapsed transition and the bash preview slices the raw text before styling; and (b) once that is true, the sliding window INHERITS the memory win instead of re-implementing it, which is why the fix comes before the policy. Frames are a separate axis: the manual path buys none today (26.6 vs 26.1 ms) while the automatic one is −23%, so the frame win belongs to the POLICY and the memory win to the FREEING.
S17. Question asked by the user and answered by the architecture: does turning H4 on make the search read the HEIGHT INDEX instead of the rows, removing H1's regression? No — the index holds heights, not text, so a corpus still has to read rendered ROWS to have anything to search; what H4 changes is HOW OFTEN it reads them (only the row whose string changed, instead of every row per frame). That is why H4 takes the regression from +100% (32.48 → 63.52 ms) down to +8% (6.65 → 7.17) WITHOUT removing it, and why the first corpus build still pays 68 ms against 55. The remaining fix is not another cache but a SEQUENTIAL ACCESS path over the index: an iterator that walks the heights in order and yields rows at O(1) amortized, turning the whole traversal back into O(n) — reading the book instead of consulting the index once per page.

User decision, verbatim: "igual como te digo no se usa mucho en general, estamos bien" — search is rare enough that H1's remaining +8% residual and the 68 vs 55 ms first corpus build are acceptable, so T15 is DROPPED rather than left pending (recorded with its mechanism and target numbers so a future revival starts from a measurement). S18. T14(b) result. The sliding window needed NO new mechanism: `ToolCollapseRow.build` already calls the renderer with `expanded: true` for a row inside the window and drops the inner component for a row outside it, which IS S15's behaviour. What was missing was Ctrl+O wired to it, so `ToolCollapsePolicy` gained `toggleExpand(available)`, returning `{kind:"legacy"}` when the setting is off (the caller keeps today's global toggle, unchanged) and flipping the MODE when it is on; the mode is session state, survives a new prompt, and `onTurnStart` keeps resetting only the legacy per-turn override — the user turns the mode on because they are WATCHING the agent work, so a reset per turn is exactly what they do not want. Two things building it taught: (1) a defect the first version had — after the mode was turned OFF a row stayed built with `expanded: true`, so Ctrl+O-off did NOT return to today; fixed by making the row honour the required mode and rebuild the inner when it changes; (2) T13's premise about `updateDisplay` handing the component back was NOT the cause of the retained memory, the preview string was. N was chosen BY MEASUREMENT over {1,5,10,15} at 500/2000/5000 turns (3 rounds, one apparatus, box NOT idle at load 5.7-6.4, declared): at 5000 turns the warm frame is 3.88 ms with no collapse against 1.73/1.46/1.44/1.50 for N=1/5/10/15, heap 87.9 MB against 67.9-68.0, lines 265,000 against 85,036-85,540. **N=10**, and the honest reason is that COST DOES NOT SEPARATE THE CANDIDATES — the whole N=1 to N=15 span is +0.1 MB and +504 lines (0.15% of the heap, 0.6% of the lines, 0.03-0.06 ms of frame) — so the middle of the tested range was kept, which is also the N every earlier table was measured with. Hypothesis discarded by that number: "a smaller window is a cost lever".
