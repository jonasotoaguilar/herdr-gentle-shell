# herdr sidebar requires the herdr plugin: auto-disable and refuse

The startup check (`lib/herdr-plugin-check.js`) notices a missing plugin and says
so once, but it never touches the sidebar option: with `sidebar=gentle` and no
plugin, nothing renders and only a later Apply fails. This feature makes the
missing prerequisite visible and consequences-free at the moment it matters.

## Specs

S1. User requirement, verbatim: "Tambien agregamos una opcion de que al arranca revisaba si tenia el plugin de herdr sino notificaba. En su lugar sacala, al arrcancar lo revisa y si ve que no esta apaga la opcion de herdr sidebar y avisa que se apago por falta de plugin de herdr, que lo instale. Si luego intenta activarla se revisa denuevo y si no lo tiene le sale denuevo el mensaje y no lo activa (similar a lo de moshi)."
S2. Startup behaviour, fixed: at session start the check still runs, and when the verdict is `missing` (or `disabled`, which is equally unusable) AND the sidebar option currently reads `gentle`, the option is turned OFF through the SAME writer the customize panel uses, and the user is told in one message that the sidebar was switched off because the herdr plugin is not installed, naming the install command. The message must say it was switched OFF and WHY — not merely that something is missing. When the plugin is present and usable, or the option is already off, startup stays quiet about the sidebar. SCOPE PRECISION, decided after the implementing unit proved the writer refuses when the plugin root cannot be resolved (see L3): a missing prerequisite may block turning a feature ON, never OFF. Therefore the switch-off converges the mode flag and the owned exclusion, and the managed `config.toml` rows are LEFT AS FOUND, with the message saying so when the block is still present — their only stripper lives in the plugin (`herdr-plugin/bin/configure.js removeManaged`), which by definition is not installed in this case, and nothing reads those rows while it is absent. `lib/gentle-sidebar.js` keeps its stricter resolve-first behaviour; this narrowing is deliberate and user-visible, not an accident.
S3. Enable behaviour, fixed and modelled on moshi: the gate runs on the ENABLE path only, BEFORE any write, and is fail-closed. Accounting for the existing `checkMoshiPrereqs` pattern (`lib/moshi-prereq.js:44`, gate at `extensions/gentle-herdr-state.ts:2573-2591`): refusing must change nothing at all — no flag file, no settings exclusion, no config.toml rows, no marker — and the switch stays off; retrying while the plugin is still missing re-emits the same message; and the message names the concrete install command. Disabling never runs the gate.
S4. Messages: the startup message and the enable refusal are two distinct strings with distinct purposes, and both name the install command. The existing alert text for a missing plugin already carries it; the refusal must carry it too rather than only stating that the plugin is required.
S5. Never a false success: if the auto-disable write fails, the user is told the true outcome (still on, and why) instead of a claim that it was switched off.

## Log

L1. User request, verbatim: the sentence reproduced as S1, sent in the message whose main subject was pi fullscreen performance.
L2. Code map gathered before writing this spec (evidence, `path:line`): the startup check is `pi.on("session_start")` → `checkAndNotifyHerdrPlugin` (`extensions/gentle-worktree-tools.ts:7552-7566`), it notifies once per session (`lib/herdr-plugin-check.js:210`), and its verdicts are `missing` / `wrong-id` / `disabled` / `version-mismatch` / `ok` / `silent` (`decideStatus`, `:105`). It never reads the sidebar option (`gentle-sidebar-mode.json`, `readSidebarMode` at `extensions/gentle-herdr-state.ts:1649`, where a MISSING file means enabled). Today, option on + plugin missing: the alert fires unconditionally, `customize status` still reports `sidebar=gentle`, the daemon does not exist, and the later Apply fails with `could not resolve the installed plugin root … Retry via /herdr-gentle:customize to converge.` (`gentle-herdr-state.ts:1932`, `:2000-2004`). The moshi precedent to copy: gate on enable only (`gentle-herdr-state.ts:2557`, gate `:2573-2591`), fail-closed PATH scan with a 5 s `status --json` (`lib/moshi-prereq.js:44`, `:76`), refusal writes nothing, and the three literals are kept byte-identical in the installed-copy mirror (`lib/moshi-prereq.js:26-29`; extension copies at `:2510/2514/2522`).
L3. The implementing unit found, before writing any code, that T1's original wording was impossible as written, and proved it with a probe: `sidebarDisable` (`extensions/gentle-herdr-state.ts:1978-1992`) resolves the installed plugin root FIRST and returns unchanged when it fails, with row convergence (`:2000-2012`) running only through `<root>/bin/configure.js --uninstall`; `lib/gentle-sidebar.js:310-320 disable()` has the identical resolve-first refusal, and the only managed-block stripper is `herdr-plugin/bin/configure.js removeManaged` (`:299-315`), which cannot exist when the plugin is missing. Probe result with the mode file at `{"version":1,"enabled":true}` and zero matching plugins: `apply("native")` → `{"changed":false,…,"text":"Could not disable: could not resolve the installed plugin root …"}`, mode file unchanged, option still ON. So the option that REQUIRES the plugin could not be switched off BY the same requirement — a lockout, and the real defect this feature exists to remove. DECISION (parent, A+D): a missing prerequisite may block turning a feature ON, never OFF; `sidebarDisable` stops aborting on an unresolvable root (remove the owned exclusion, write mode=false, skip `configure.js`), the managed rows stay as found and the message says so, and `lib/gentle-sidebar.js` keeps its stricter contract untouched. Option B (inlining a managed-block stripper) was declined: it would fork a contract away from its owner for a case where the plugin is absent and nothing reads those rows. S2 was narrowed accordingly, on purpose. The tests extend the EXISTING suites — `tools/gentle-sidebar-toggle.test.js`, `tools/gentle-moshi-toggle.test.js`, `tools/herdr-plugin-check.test.js` — because the two paths originally authorized (`tools/customize-sidebar.test.js`, `tools/customize-moshi.test.js`) do not exist in this repo; creating them would have duplicated live harnesses.
