# Reset every customize option to its default

The customize panel can change three options and has no way back: today there is
no command, key or provider method that restores factory values, and each
option's default lives at its own read site. This feature adds one explicit
reset, modelled on the upstream gentle-shell customize.

## Specs

S1. User requirement, verbatim: "Tambien agrega a herdr customize una opcion para volver todo a default (como lo tiene el customize de gentle-shell)."
S2. What "everything" means, fixed: the three user-visible options the panel owns — `sidebar`, `moshi` and `worktree` — each returned to the default its own read site defines: sidebar missing file = **enabled/gentle**; moshi missing file = **off**; worktree missing = **enabled**. Because two of them have effects outside their flag file, the reset must converge them through the SAME writers the panel's own actions use rather than deleting files behind their backs: the moshi reset must also clear its Pi `settings.json` exclusion, and the sidebar reset must also let its Herdr `config.toml` managed rows and marker converge. A reset that leaves those behind is a half-reset that lies about the state.
S3. Written, not deleted: following the upstream precedent (`extensions/gentle-shell.ts:2382-2406`, which calls `writeVisualSettings(structuredClone(DEFAULT_VISUAL_SETTINGS), home)` and friends and NEVER deletes files), the reset WRITES each default explicitly through the existing writer. It does not unlink the JSON files, because the read sites only agree on "missing" by accident and the sidebar path carries out-of-band state.
S4. Honest partial failure: the upstream reports `Partial reset: visual changed, banner unchanged, animation unchanged. <error>`; this reset does the same — per-option success or failure is reported, and a failed option is named as unchanged rather than silently skipped. A total failure says nothing was changed.
S5. Interaction: the reset is one row in the panel with a clear label, it is not available when there is nothing to reset (all options already at their defaults) and says so, and it never depends on the herdr plugin being installed — resetting to defaults must always be possible, including when the sidebar is being switched off for a missing plugin.

S6. User requirement, verbatim: "en default recuerda que si sidebar no tiene el plugin de pi pasa a apagado, es requisito tenerlo para poder encenderlo" — clarified in the same message as "plyugin de herdr para sidebare", i.e. the HERDR plugin is what the sidebar requires. Fixed: the sidebar's default is CONDITIONAL. With the herdr plugin installed and usable, its default is ON. With the plugin missing, its default is OFF, and enabling it is refused until the plugin exists — so a reset performed without the plugin must leave it OFF and must NOT present that as a failure, because OFF is the correct default in that state. The notice must say WHY it stays off and name the requirement, rather than reading as "the sidebar could not be reset". Two consequences the implementation must respect: (a) the nothing-to-reset case is judged against the default that APPLIES in the current state, so with the plugin absent a sidebar already off is nothing to reset, while with the plugin present an off sidebar IS something to reset; (b) the honest partial notice keeps naming the real install command as the fix.

T4 | S6 | implement | done | Make the conditional default legible. The reset already leaves the sidebar off without the plugin and names the install command (proved by the existing test), but it reports it inside `Partial reset: sidebar unchanged, …`, which reads as a failure when OFF is in fact the correct default in that state. Report that case as the default applying, not as a partial miss, and state that the herdr plugin is required to enable the sidebar. Judge the nothing-to-reset case against the default that applies in the current state, in both directions: without the plugin an off sidebar is nothing to reset, with the plugin present an off sidebar is something to reset. Keep the install command in the message. Tests: the plugin-missing reset reads as the default applying and never as a partial failure; nothing-to-reset with the plugin absent and the sidebar off; something-to-reset with the plugin present and the sidebar off; and the install command still present in both messages.
